# Дизайн базы данных

Схема: [`db/schema.sql`](../db/schema.sql) (SQLite/Drift). Проверена скриптом —
выполняется без ошибок, вставка/JOIN по всем связкам работает (кандзи →
слово → юнит → SRS-карточка → запись повторения).

## Ключевые решения

### 1. Контент и пользовательские данные — разные миры

- **CONTENT** (кана, кандзи, слова, частицы, грамматика, юниты) — общий для
  всех, поставляется вместе с приложением как отдельный бандл
  (`content.db`), обновляется независимо от прогресса пользователя.
  Не требует аккаунта и не участвует в синхронизации как «пользовательские
  данные».
- **USER DATA** (профиль, SRS-карточки, журнал повторений, прогресс по
  юнитам, личный словарь) — приватные, живут локально всегда, и при
  наличии аккаунта синхронизируются с облаком (Supabase/Postgres).

Такое разделение позволяет обновлять контент (добавить кандзи, поправить
пример) без миграции пользовательской базы, и наоборот.

### 2. `content_items` — единая «супертаблица»

Кана/кандзи/слово/частица/грамматика — разные таблицы, но у каждой записи
есть одна строка в `content_items`. Это заменяет полиморфные ссылки
(`item_type` + `item_id` без реального FK) на нормальный внешний ключ:
SRS, юниты, личный словарь, разбор предложений — всё ссылается на
`content_items.id`, и SQLite/Postgres честно проверяют целостность.

### 3. Кандзи не существует в одиночку

Реализовано через связи, а не текстовое поле:
- `kanji_radicals` — из каких радикалов состоит кандзи (мнемоника).
- `word_kanji` — в каких словах встречается кандзи (дзюкуго).
- чтения (`on_yomi`/`kun_yomi`) хранятся при кандзи каной, а не отдельно.

Карточка на кандзи в SRS всегда идёт с контекстом: значение, чтение через
кану, слово-пример — это задаёт сама схема, а не UI поверх неё.

### 4. Частицы и грамматика — с полной теорией и живыми примерами

`particles.long_theory` и `grammar_points.explanation` — полноценный
текст (markdown), а `sentence_content_items` привязывает каждую частицу и
конструкцию к реальным предложениям из `sentences`. `confusable_with` /
`related_grammar_ids` — заготовка под сравнительные таблицы (は vs が).

### 5. `exercise_types` — отдельная таблица, не enum в коде

Один и тот же кандзи/слово может иметь несколько SRS-карточек — на
значение, на чтение, на прослушивание, позже на прорисовку (`stroke_write`
для Android). Добавление нового типа упражнения — это новая строка в
таблице, а не миграция схемы `srs_cards`. У каждого типа есть `pillar`
(reading/listening/speaking/writing) — это и даёт разбивку прогресса по 4
столпам, которую ты просил в онбординге.

### 6. Дорожная карта — DAG, а не жёсткая цепочка

`unit_prerequisites` — таблица связей многие-ко-многим, а не одно поле
«предыдущий юнит». Веха «N5 пройден» может требовать сразу несколько
юнитов одновременно — проверено в smoke-тесте.

### 7. Синхронизация: `review_log` как источник истины

Самая частая операция — повторение карточки. `review_log` — это
append-only журнал событий (кто, что, когда, с какой оценкой повторил).
У записи UUID генерируется на клиенте — значит синк Windows ↔ Android
идёмпотентен и почти никогда не конфликтует: обе стороны просто обмениваются
новыми строками.

`srs_cards` — это кэш текущего состояния (due date, stability,
difficulty и т.д.), который в теории полностью выводится пересчётом из
`review_log`. На практике синкается и он, но `review_log` — то, что
обязано быть источником истины при любом конфликте.

`unit_progress`, `user_vocab`, `daily_activity` — низкочастотные
таблицы, конфликты по ним маловероятны (обычно пользователь занимается на
одном устройстве последовательно), поэтому для них ок простой
last-write-wins при синке.

### 8. Онбординг — данные, не хардкод

`user_profile.weight_listening/speaking/reading/writing` — 4 веса из
онбординг-теста. `comprehension_goal_pct` — nullable, пользователь может
не ставить числовую цель вовсе. `placement_level` — результат
плейсмент-теста для тех, кто не начинает с нуля.

## Что осознанно отложено (не в первой версии схемы)

- Pitch-accent — поле `pitch_accent` в `words` уже есть, но механика
  тренировки по нему — отдельная фаза.
- Полноценный FSRS-планировщик — поля `stability`/`difficulty` заложены,
  сам алгоритм подключается в коде на Фазе 1.
- Мультипрофильность на одном устройстве — таблица `users` уже это
  допускает, но UI переключения профилей не проектировали.
- Права доступа/шаринг в Supabase (RLS-политики) — отдельная задача Фазы 3.
